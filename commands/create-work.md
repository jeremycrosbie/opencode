You are creating an epic and stories in Shortcut via the local story proxy.

Before doing anything, you need two pieces of information:
1. **The proxy base URL** (e.g., `http://localhost:8000`)
2. **The path to a plan markdown file** generated by /plan-work

Check if $ARGUMENTS contains both a URL and a file path. If only a file path is provided (or only a URL), ask the user for the missing piece. If neither is provided, ask for both.

Once you have both, execute the following steps:

1. **Read and parse the markdown file.** The markdown file can contain more than just stories, so look for content formatted like the following:

```
# Epic: <epic name>

<epic description>

## Stories

### <Feature|Bug|Chore>: <story name>
**Estimate:** <number from the scale: 0, 1, 2, 3, 5, 8>
**Labels:** <comma-separated label names, optional>
**Blockers:** <pipe-separate list of story names blocking the implementation of this story>

<story description>

#### Acceptance Criteria
- [ ] <criterion>
- [ ] <criterion>
```

2. `GET /capabilities` will explain what operations are available.
3. **Create the epic** by calling `POST <base_url>/epics` with the epic name and description.
4. **Create each story** by calling `POST <base_url>/stories` for each story in the file, using the epic_id returned from step 2. Track a mapping of `story name → story id` as you go.
5. **Create blocker links** — after all stories are created, for each story that had a `**Blockers:**` line, call `POST <base_url>/stories/link` for each blocker relationship.

For each story, map the markdown fields to the API request:
- Story name: the text after the type prefix (e.g., `Feature: Foo` → name is `Foo`)
- `story_type`: lowercase type prefix (`feature`, `bug`, or `chore`)
- `description`: the text between the metadata lines and the Acceptance Criteria section
- `estimate`: the number on the `**Estimate:**` line (omit from request if not present)
- `labels`: comma-separated values on the `**Labels:**` line (omit from request if not present)
- `tasks`: each `- [ ]` checkbox item under `#### Acceptance Criteria`
- `epic_id`: the ID returned when creating the epic
- **Do NOT include blockers in the story creation request.** Blockers are handled in step 4.

The story name→id mapping from step 3 should use the story name WITHOUT the type prefix as the key (e.g., `Feature: Foo` → key is `Foo`). If a `**Blockers:**` line is present but empty, treat it as having no blockers (skip it).

For each blocker link (step 4), parse the `**Blockers:**` line as a pipe-separated list of story names. For each blocker name, look up the story ID from the name→id mapping built in step 3. Then call:

```
POST <base_url>/stories/link
{
  "subject_id": <blocker_story_id>,
  "object_id": <this_story_id>,
  "verb": "blocks"
}
```

This means: "blocker story blocks this story".

If a blocker name doesn't match any created story, warn the user but continue with the remaining links.

Use `curl` to make the API calls. Create the epic first, then create stories sequentially, then create blocker links.

After everything is created, summarize what was created with links (app_url) for each item, and list any blocker relationships that were established.

If any story creation request fails, stop and report the error — do not continue creating remaining stories. If a blocker link fails, report the error but continue with remaining links.

Do not modify files.
